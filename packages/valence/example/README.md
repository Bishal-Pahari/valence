# valence_example

The existing `haptics.tap` now comes from the local `plugins/haptics` Dart package,
with its own schema fragment, matching npm types and setup notes. `main.dart`
registers it in the generated `ValenceBuiltins`; it contains no haptic handler.
The wire shape and schema version stay unchanged. The built-in `open.external`
also uses the plugin API and keeps the runtime's scheme allowlist.

A whole Valence host, to show how little of one you write.

Everything the spec calls the host — the loopback server with its per-launch nonce, the canonical manifest
check order, the activation state machine with its rollback, the SQLite store and its seed import, sync
with its lease, the bridge trust boundary, the WebView with its navigation lock and back gesture — is in
the [`valence`](https://pub.dev/packages/valence) package. This app is the part that is genuinely an app's:

| File | What it is |
|---|---|
| [`lib/main.dart`](lib/main.dart) | The host. About twenty lines: open the runtime with the generated config, and put `ValenceApp` at the root. |
| `AppHandlers` in the same file | Registers the local haptics plugin; all method adapters are inherited from the generated `ValenceBuiltins`. |
| [`valence/bridge.schema.json`](valence/bridge.schema.json) | The app's bridge IDL. Config `plugins` merges the separate haptics fragment into it. |
| [`plugins/haptics`](plugins/haptics/) | A Dart handler package, schema fragment, matching npm types and native setup notes. |
| [`valence/valence.config.json`](valence/valence.config.json) | App id, keyring, OTA and sync bases, the `plants` read-only bucket and the `shelf` writable one. |
| [`lib/valence/*.g.dart`](lib/valence/) | Generated by `valence codegen`. Never edited. |
| `android/`, `ios/` | The platform setup a Dart package cannot write: the Android cleartext config for `127.0.0.1` **only**, the backup rules excluding `valence/`, the iOS ATS loopback exception and the backup exclusion in `AppDelegate`. |
| [`pubspec.yaml`](pubspec.yaml) | The `valence` dependency, and the three asset lines — Flutter asset directories are **not** recursive, so both `builtin` lines are needed. |

## Run it

For the R9 live-development demo, run `npm install` in `dev-web`, then from this example root
run `node ../../../.claude/skills/valence/scripts/valence.mjs dev --web-dir dev-web`.
In another terminal run the printed Flutter command. Tap the counter, edit `dev-web/message.js`
and verify the label changes while the counter stays put. The HMR callback also writes a native
preference through the generated typed bridge and logs its success. The alias in `vite.config.mjs`
uses this repository's bridge source; an adopter uses the ordinary npm package. Stop the dev
server and rebuild without the define for signed-bundle tests. iOS remains untested.

The schema-14 example has two image-sharing buttons: one sends small inline PNG
bytes and the other names `share.png` in the signed bundle. Both include a caption.
The result reports target selection, dismissal or an unavailable outcome; no
delivery is claimed. The iOS path is experimental and untested.

```sh
flutter pub get
flutter test              # the wiring tests
flutter build apk --debug
```

The OTA and sync hosts in the config are `.invalid`, so nothing leaves the machine: the app serves its
built-in bundle and reads the seeded `plants` bucket offline.

## What the tests prove

[`test/example_test.dart`](test/example_test.dart) covers the half the package's own suite cannot: that
the generated delegations really reach the runtime (a `data.put` that lands in SQLite and comes back from
`data.list`), that this app's own method reaches the dispatcher, and that the policies the package owns —
a read-only bucket, a reserved `prefs` key, a `javascript:` URL — are enforced through the generated path.

The contracts §8 matrix is the package's suite, one directory up. An app does not re-test it.

## Not a device test

The R12 tooling check on 2026-10-21 separately ran this example on Android: seeded batch reads,
two queued writes and a queued delete showed the same pending count in the page and SQLite.
See [the validation record](../../../docs/r12-validation.md). The pre-JNI dependency range resolved
`path_provider_android` 2.2.23. Its prior local override is removed; the runtime carries the constraint.

A green `flutter test` is **not** evidence that the store opens on a phone: it runs on
`sqflite_common_ffi`, which accepts pragmas that Android's `SQLiteDatabase` rejects. Android is the tested
platform for Valence; **iOS is experimental and untested**.

## Native HTTP demo

Native HTTP was added at built-in schema 4; the combined example schema is 15.
`http.origins` grants only `http://127.0.0.1:8787` for the local demo. Run the
reference adapter in `examples/rest-sync-adapter/`, then
`adb reverse tcp:8787 tcp:8787`. Set its synthetic `ADAPTER_TOKEN` through the
Login form and tap `http.request`. `GET /rpc` returns status without echoing
the token; the other button proves an unlisted origin is denied. No CORS headers
are needed. Use HTTPS for remote APIs. Native Dart HTTP can send a token to an
explicit cleartext origin even in release builds despite Android's network
security XML. The default example therefore grants no off-device HTTP origin.
The offline bundle and seed still work without that server.

For the release-device transport probe and its synthetic-only credential, see
[R23 validation](../../../docs/r23-validation.md).

## R8 layout probe

The signed page displays app.appearance and logical insets, pads content with the host variables, uses 48px buttons and exposes optional fontScale through app.info. Rotate, resize, change font size and toggle system dark mode without reloading. See [accessibility](../../../docs/accessibility.md). iOS remains experimental and untested.

## Task restoration

Schema 8 adds `state.save({json})` and `state.restore()` for a task-local UI blob (65,536 JSON UTF-8 bytes). ValenceApp restores the local path/query/hash after OS process reclamation. Explicit task closure starts fresh; a different bundle seq clears the snapshot. Save promptly and keep durable records in SQLite. iOS is experimental and untested. [Guide](https://getvalence.pages.dev/docs/guides/state-restoration/).

Task snapshots are bound to the native account as well as the signed bundle: switching or signing out clears the route and draft, including stale OS snapshots. Refresh and first-account adoption retain the live draft.

## Deep-link demo

The R6 surfaces were added at schema 9. This merged example reports schema 15 and accepts `valence-example://app` and `https://links.example.invalid`. Native Android filters and experimental iOS registrations are included. The page shows the routed path/query/hash and uses the wire protocol directly, matching the rest of this no-bundler demo. Production apps use `onLink()` from their generated client. See [setup](../../../docs/deep-links.md). The placeholder HTTPS domain cannot verify; forced approval tests delivery only.


## Permissions demo

Schema 10 adds a Permissions section: choose any of the seven kinds, Check, Request or open App settings. Resume deltas appear separately. All kinds are declared solely for this demonstration; production apps must enable and declare only the kinds they use. The Android manifest and iOS SPM usage strings are wired; iOS remains experimental and untested. [Setup guide](https://getvalence.pages.dev/docs/guides/permissions/).



## Local reminder demo

The example schema is 13, with notification methods and events since 11 and notifications.enabled set to true. Allow reminders, then schedule 15 seconds ahead: the page shows exact or inexact, displays native pending requests, cancels ID 42 and records warm tap/action or the consumed cold initial response. Images use a tiny PNG; Done and Snooze open the UI and report an action without automatically changing app data. The Android platform files include receivers, a status drawable and desugaring. iOS/AppDelegate is implemented but experimental and untested. See [setup](../../../docs/local-notifications.md).

## Remote push demo

Remote push is opt-in in schema 12: `push.token`, passive/explicit `push.permission`, consuming `push.initial`, `push.received`, `push.tapped` and `push.tokenChanged`. Firebase runs only in configured hosts; exact data-only sync hints use the existing native sync without touching OTA state. Android notification images use FCM background display; foreground messages reach the page. **Device validation is blocked: needs Firebase project. iOS/APNs is experimental and untested.** Add your own `android/app/google-services.json`, then `flutter run --dart-define=VALENCE_PUSH=true`. The Google services Gradle plugin is conditional on that file. The page checks/requests permission and reports registration without displaying the token. [Full setup](../../../docs/remote-push.md). The checked-in signed built-in bundle contains the push controls; it stays offline and reports E_UNSUPPORTED until configured. iOS hosts must target 15.0 or later for the Firebase dependencies.

Schema 15 adds nullable AppInfo.builtins, SyncStatus.reason and BundleStatus.urgent. Older hosts omit them. See [capability revisions and durable status](https://getvalence.pages.dev/docs/guides/capabilities-and-status/).

Development startup logs `dev: serving upstream <origin>` and says OTA checks, trials, ready
commits and `bundle.applyUpdate` are disabled. Each skipped ready, signed reload, update check
or apply call also logs a `dev:` diagnostic. A successful call in this mode does not prove an
OTA transition. Restart without `VALENCE_DEV_URL` for signed offline and rollback validation.
