# valence

`Valence.shareImage` backs schema-14 `share.image`: bounded PNG/JPEG bytes or an
active signed bundle image, plus a caption. The runtime checks paths, size, magic
and bundle integrity before opening native sharing. Results report selection,
dismissal or an unavailable outcome, never delivery. See
[image sharing](https://getvalence.pages.dev/docs/guides/image-sharing/).
iOS sharing remains experimental and untested.

The Flutter host runtime for [Valence](https://getvalence.pages.dev): your web app runs inside a native
app as a **signed over-the-air bundle**, on top of an **offline-first SQLite** store with incremental sync
and a **typed bridge**. UI changes ship without an app-store review; the native shell is reviewed rarely.

This package is the whole host. You get the loopback server with its per-launch nonce, the canonical
manifest check order, the activation state machine with automatic rollback, the SQLite store and its seed
import, sync with its lease, the strict bridge decoding, and the WebView with its navigation lock, back
gesture and console capture.

Your app supplies two things: its generated config, and its own native bridge methods.

Task snapshots are bound to the native account as well as the signed bundle: switching or signing out clears the route and draft, including stale OS snapshots. Refresh and first-account adoption retain the live draft.

## Task restoration in 0.4

Schema 8 adds `state.save({json})` and `state.restore()` for at most 65,536 JSON
UTF-8 bytes of task-local UI state. ValenceApp installs its own RootRestorationScope
and restores the local path/query/hash after OS process reclamation. A fresh task
after explicit closure starts empty; an update or rollback clears the snapshot.
Use SQLite for durable records and secure storage for secrets.
[Guide](../../docs/state-restoration.md). The iOS FlutterViewController needs a
restoration identifier in Main.storyboard; iOS is experimental and untested.


## Setup

Migrating custom notification events requires preserving their payload types as well as methods.
Regenerate config to exclude pre-11 events from automatic native emission, and pass
`notificationEventAdapter` to `Valence.open` for your generated legacy event builder.
Cold taps stay consume-once and need the same app-owned conversion.
[Migration recipe](https://getvalence.pages.dev/docs/guides/local-notifications/#keeping-a-shipped-custom-tap-event).

Seed imports record completion separately from row insertion. A locked completion marker retries
up to five times, one second apart; exhausted retries retain rows and leave the marker for the
next launch. [Recovery and log meanings](../../docs/seed-recovery.md). No app codegen change is needed.

For debug-only HMR, `valence dev` binds loopback by default. A physical-device LAN
target requires `--allow-lan`, which acknowledges a cleartext full-bridge trust grant;
it provides no encryption or authentication. Start your web dev server and run
`flutter run --debug --dart-define=VALENCE_DEV_URL=http://10.0.2.2:5173`.
The loopback proxy injects the normal bridge nonce and forwards HMR WebSockets. Release/profile
builds exclude this path. Use a separate development app id and test accounts; the page has the
full native bridge and SQLite access. See the [development guide](https://getvalence.pages.dev/docs/guides/development/).

Native features can also come from a `ValencePlugin` package. List its schema
fragment in config `plugins`, regenerate, and pass its instance to the generated
`ValenceBuiltins(valence, plugins: [...])`. Regenerated handlers check every fragment namespace and exact
method registration at construction in all build modes; missing registrations
throw `StateError` naming the fix. Test construction of your real app handlers.
Doctor lists these requirements as a warning, since it cannot execute registration.
Generated strict decoding owns the bridge boundary; the registry is not a WebView dispatcher. The plugin owns
native setup, initialization and cleanup, and needs a store release. See
[Writing a Valence plugin](https://getvalence.pages.dev/docs/guides/plugins/) and
the example's `plugins/haptics` package. The built-in `open.external` uses this
API too, with its existing scheme restrictions and reserved owner.

```bash
flutter pub add valence
npx valence codegen
```

```dart
import 'package:flutter/material.dart';
import 'package:valence/valence.dart';

import 'valence/bridge.g.dart';
import 'valence/config.g.dart';

Future<void> main() async {
  final valence = await Valence.open(valenceConfig);
  final handlers = AppHandlers(valence);
  runApp(
    MaterialApp(
      home: ValenceApp(
        valence: valence,
        dispatch: (raw, nonce) => bridgeDispatch(handlers, raw, nonce: nonce),
      ),
    ),
  );
}
```

`valenceConfig`, `bridgeDispatch` and `ValenceBuiltins` are generated by `valence codegen` from your
`valence/valence.config.json` and `valence/bridge.schema.json`. Your own methods go in one class:

```dart
class AppHandlers extends ValenceBuiltins implements BridgeHandlers {
  AppHandlers(super.valence);

  @override
  Future<void> hapticsTap() async => HapticFeedback.lightImpact();
}
```

`ValenceBuiltins` already implements `app.*`, `data.*`, `prefs.*`, `sync.*`, `secure.*`, `auth.*`,
`open.external` and `bundle.*` by delegating to the runtime, so only what is app-specific is left
abstract.

## What you still do yourself

The package cannot write native project files, so these are yours:

| | |
|---|---|
| **Assets** | Declare `assets/valence/builtin/`, `assets/valence/builtin/files/` and `assets/valence/seed.db` in `pubspec.yaml`. Flutter asset directories are **not** recursive, so the two `builtin` lines are both needed. |
| **Android `minSdk`** | 23 or later. `flutter_secure_storage`, which holds the bearer token and `secure.*` (contracts §4.4), needs the Keystore APIs added there. |
| **Android cleartext** | `res/xml/network_security_config.xml` permitting cleartext for `127.0.0.1` **only**, referenced from `AndroidManifest.xml`. |
| **Android backups** | `dataExtractionRules` and `fullBackupContent` excluding `valence/`. A restore should start clean from the built-in bundle. |
| **iOS ATS** | The App Transport Security loopback exception. Never `NSAllowsArbitraryLoads`. |
| **iOS backups** | `NSURLIsExcludedFromBackupKey` on the `valence/` directory, from `AppDelegate`. The SQLite file lives *outside* it and is backed up, because it holds user data. |
| **Background sync** | `Valence.backgroundSync(valenceConfig)` is the callable; registering it with `workmanager` or `BGTaskScheduler` is yours. The package deliberately does not depend on `workmanager`, which applies the Kotlin Gradle Plugin and warns on every Android build. |
| **Native value** | At least two of the capabilities in contracts §6, or Apple rejects the app as a repackaged website (guideline 4.2). |

## Things that cost someone a day

- **`PRAGMA journal_mode = WAL` must go through `rawQuery`, not `execute`.** The package does this.
  `sqflite_common_ffi`, the factory `flutter test` uses, accepts `execute`, so no unit test catches it and
  the app dies on its first launch on a phone. Check `store.isWal` in your logs.
- **Never close the database.** sqflite keys open databases by path *inside the platform plugin*, so a
  `close()` in a background isolate invalidates the handle the UI isolate holds. There is deliberately no
  `close` on `ValenceStore`. A background isolate needs `DartPluginRegistrant.ensureInitialized()` first.
- **Build the web app with an absolute base** (`base: '/'` in Vite). The SPA fallback serves the entry page
  at any depth, so a relative asset URL 404s on every nested route — a blank screen with nothing in the
  log, visible only after a reload or a back gesture. `valence bundle` warns about it.
- **The bridge is not a path for bytes.** Messages are capped at 256 KB of UTF-8 each way. Native bytes
  reach the page through `valence.publishHostFile(...)`, which serves them under the reserved `/_host/`
  prefix with `nosniff` and a locked-down CSP.
- **`app.ready()` is what commits an OTA release.** A bundle that never calls it fails its trial twice and
  is rolled back. Call it after the first meaningful paint.
- **A WebView eviction kills the app on Android, and 0.4 cannot stop it.** The page runs in a separate,
  lower-priority process; under memory pressure the OS kills that one, and because no released
  `webview_flutter_android` exposes `onRenderProcessGone`, the WebView then kills your process too. No
  Dart code runs, so nothing logs it — identify it from `dumpsys activity exit-info` (renderer
  `LOW_MEMORY`, then your app `SIGNALED/9`). Because no Dart code runs, an eviction **during a trial
  costs that release a strike** — two of them retire a healthy release on that install, so roll out to
  10% first. Where the platform does report the loss, the host reloads the same bundle at the same route
  and spends no strike. Keep anything the user would miss in SQLite. See contracts §3, "Renderer loss",
  and the
  [startup diagnostics guide](https://getvalence.pages.dev/docs/guides/startup-diagnostics/).

## Rollback

An OTA bundle gets one trial. If `app.ready()` does not arrive within 15 s of foreground time, or the
process dies first, that is a strike; two strikes and the seq goes into `bad` for that install, for ever,
and the previous bundle is served again. Nothing you have to wire up.

To undo a bad release, **roll forward**: re-release the last good web commit, which gets a new, higher
seq. Pointing the channel at an older seq only cancels pending downloads.

## Testing

For startup stalls and database waits, see [Startup diagnostics](https://getvalence.pages.dev/docs/guides/startup-diagnostics/).
The existing logger reports `Valence.open` phase timings and database operations pending
for ten seconds, without changing retries or transaction behavior. `startup: complete`
means open returned, not that the WebView painted or a trial committed.

The generated-Dart CLI gate compares `ValencePluginRegistry.reservedNamespaces`
with the CLI's exported `PLUGIN_RESERVED` set. Update vendored tooling and
regenerate when upgrading the runtime. Malformed typed plugin results are
`E_INTERNAL`; parameter failures remain `E_PARAMS`. Separate npm plugin types
are hand-maintained, and plugins have native host privileges; see
[the plugin guide](https://getvalence.pages.dev/docs/guides/plugins/).

`flutter test` in this package runs the contracts §8 matrix: every canonical check rejecting, the state
machine's strikes and promotions, the server's three branches in order, the store, sync and the lease.

[The host widget tests](https://getvalence.pages.dev/docs/guides/host-widget-tests/) pump the real
`ValenceApp` against a test-only WebView platform, with signed bundles, SQLite and a loopback socket, so
`flutter test test/app_widget_test.dart` covers the lifecycle, the startup resume guard, the navigation
lock, bridge nonce forwarding, event buffering and the ready timer.

A green unit suite is **not** evidence the store opens on a phone — see the first gotcha above. The §8
integration row is what covers that, and the widget harness replaces only the native WebView calls, so
it proves host *policy* and never the OS WebView's own behaviour. iOS stays experimental and untested.

## Versioning

The bridge IDL and the manifest `format` are additive only. This package's version is independent of your
schema's `BRIDGE_VERSION`.

A method of your own that nothing calls any more can be marked `"retired": true` in the schema: the name
and its shape stay, so `has()` and every shipped bundle are unchanged, and codegen answers it with
`E_UNSUPPORTED` from `ValenceBuiltins` instead of leaving an abstract member — which is what lets the dead
native code go. A built-in, `app.ready`/`app.info` and a plugin method cannot be retired.
